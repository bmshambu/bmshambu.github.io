Architecture proposal · RFP GraphRAG

Scale to 10,000 documents by adopting the Cosmos DB storage pattern

Borrow the persistence layer from Microsoft's CosmosAIGraph reference architecture — without taking on its Java / SPARQL graph stack. The pipeline, UI, and LLM layer stay exactly as they are today.

2026-07-09 status: proposal effort: 3–5 days risk: low
RECOMMENDED

Option A — storage pattern only. Move persistence from JSON files to Cosmos DB NoSQL containers with per-document upserts and targeted queries. This removes every identified 10k-doc blocker while touching none of the extraction pipeline, graph algorithms, or UI. Full CosmosAIGraph adoption (Java graph service, SPARQL, OWL ontology) stays open as a later step — the document schema is deliberately shaped to feed its triples-builder if we ever need it.

Trade-offs

Option A — pros and cons

Pros

  • Kills the O(N²) write problem — upserts per document instead of rewriting a growing file 10,000 times.
  • Query latency stays flat — targeted Cosmos queries replace parse-everything-per-question; no more 10–30 s loads.
  • Numeric filters move to the database — "budget over 2M" becomes a WHERE clause, not 300K tokens of prompt.
  • Jobs survive restarts — checkpoint/resume for long 10k-doc extraction runs; safe beyond one replica.
  • Nothing user-visible changes — same three tabs, same pipeline, same models; a storage-layer swap behind an interface we already have (storage.py precedent).
  • Future-proof both directions — schema feeds CosmosAIGraph's triples-builder (option B) and carries a graph_id for theme-partitioned graphs.
  • Vector search is one step away — DiskANN index on the chunks container upgrades retrieval without another migration.

Cons & mitigations

  • New Azure dependency + cost. Serverless tier ≈ single-digit $/month at this scale; autoscale only if query volume grows.
  • Local development needs Cosmos. Cosmos DB emulator or a keep-files fallback behind the same storage interface (same pattern as FolderSource vs AzureBlobSource today).
  • Graph rebuild reads all entities once. One bulk read per rebuild (seconds), then cached in process — vs every query paying that cost today.
  • Doesn't add multi-hop SPARQL or intent routing. Deliberate — that's Option B's scope, unlocked later without re-migration via the staged path.
  • Community summarisation cost at 500+ communities is unsolved by storage alone. Pair with theme-partitioned graphs (see migration_strategy.md) — per-theme rebuilds re-summarise only what changed.

Stage 2 — after the storage move

Theme-partitioned graphs with a routing layer

Instead of one monolithic 10k-doc graph, build one knowledge graph per theme (1k–5k docs each). The blob layout already encodes the boundaries — Oracle, SAP, Workday, Salesforce, Audit-Private, Audit-Public — so partitioning is natural, not invented. The Cosmos schema above carries a graph_id field for exactly this reason: stage 2 needs no second migration.

Why partition by theme

  • Incremental everything — new docs in one theme rebuild one small graph and re-summarise only its communities. Monolithic rebuilds reshuffle community IDs corpus-wide.
  • Scale pressure drops 10× — 5–30k entities per graph keeps NetworkX + Louvain in-process and the visualisation renderable.
  • Retrieval precision — budget questions about Oracle never wade through Workday entities; the financial table stays theme-sized.
  • Access control falls out free — Audit-Private becomes a restricted graph, not a filtering problem.
  • Solves the community-count problem — the one cost issue storage alone doesn't fix (500–1,500 communities to summarise).

Design guardrails

  • Route to N graphs, never "the one right graph". Cross-theme comparisons require fan-out with decomposed sub-questions, or they get worse than today.
  • theme-context.md is a table of contents, not a knowledge store. Auto-generated after each theme rebuild (from entity histograms + community titles), capped ~400 words, with a preserved human-edited block for routing hints ("Audit-Private — never auto-route"). If the router starts answering from it, answers bypass the graphs and lose citations.
  • Entity fragmentation needs the global entity index. "SAP S/4HANA" exists in four graphs; the index (entity → graphs, a few MB) restores name-based lookup and doubles as the router's free deterministic signal.
  • Contexts must state what's distinctive. Vague overlapping descriptions make the router select everything — the generation prompt forces "what can ONLY this theme answer?"
